# 旅の提案 (荷物・季節・プラン)

## 目的

旅に既に集まっている材料 — 拠点の設備、行き先、旅の日付、出発地点 — から、
利用者が手で埋めていた 3 つを提案する。

1. **設備と行き先から荷物を決める。** 乾燥機があるなら着替えは少なくてよい。プールや海があるなら水着が要る。
2. **交通手段を軸にプランを決める。** 移動時間と滞在時間が 1 日に収まる範囲でしか予定を積まない。
3. **季節柄を反映する。** 秋なら紅葉、夏なら日避け。

## 原則: 提案は DB を変えない

3 つとも **プレビュー → 採用** の 2 段で動く。
`/suggest` は読み取りだけで、旅の持ち物リストも日程も変わらない。
書き込むのは `/adopt` だけで、ユーザが選んだ分しか反映しない。

プランの採用は **上書き** である。案に含まれる日の `itinerary_items` と `route_legs` を消してから入れ直す。
案に含まれない日は触らない。上書きであることを画面で確認してから実行し、API も `confirm=true` を要求する。
採用 API はリクエスト全体を先に検証し、追加・削除を単一トランザクションで行う。
途中の行が不正、または DB 更新が失敗した場合に、既存の持ち物や旅程だけが部分的に消えることはない。

## 荷物の提案

照合の材料は「拠点の設備 (`place_facilities`)」と「旅の場所の名前・カテゴリ・要約」の両方。
海水浴場やスキー場は宿の設備ではなく行き先そのものなので、設備だけを見ていると水着が出ない。

効果は 3 方向に出る。

| 方向 | 例 |
|---|---|
| add | プール → 水着・ラッシュガード・濡れ物用の袋 |
| drop | 大浴場 → バスタオルは備え付けなので持参不要 |
| clothingCap | 乾燥機 → 着替えは泊数分でなく 2 日分でよい |

着替えの既定は「泊数 + 1 日分」。`clothingCap` があるとそこまで減らし、
「本来 5 日分だが、現地で洗濯できるので 2 日分に減らせる」と理由に書く。

同じ荷物が複数の由来から出たら (日焼け止め = 猛暑 + スキー) 1 件に束ね、由来を並べて数量は多い方を採る。

ルールで拾いきれない分は LLM が足す。LLM が失敗しても提案は成立し、
ルール由来だけになったことを `warnings` で伝える (黙って減らさない)。

## 季節の提案

季節ラベル (春/夏/秋/冬) とは別に、支度の境で区切った **気候ウィンドウ** を持つ。
紅葉は 10 月中旬から、猛暑は 7 月中旬からで、暦の季節とずれるため。

`cherry_blossom` / `pollen` / `rainy` / `heat` / `typhoon` / `autumn_leaves` / `cold` / `snow`。
旅の開始日から終了日までと各ウィンドウの重なりを見るので、両端が期間外でも旅行中に梅雨などをまたげば支度が出る。

ウィンドウは荷物 (日傘・カイロ・折りたたみ傘) と、読み物としてのヒント (紅葉は午前が空いている) の
両方になる。ヒントはプラン提案にも渡り、各日のメモの材料になる。

## プランの提案

各日の骨格は「出発地点 → 訪問 … → 帰着地点」。

| 日 | 開始 | 終了 |
|---|---|---|
| 初日 | 出発地点 (自宅/集合地点) | 拠点 |
| 中日 | 拠点 | 拠点 |
| 最終日 | 拠点 (チェックアウト後) | 出発地点 |

拠点が無ければ出発地点、それも無ければ最初の候補地を起点にする。
最終日の開始時刻は拠点のチェックアウト時刻より前にならない。

積み方は貪欲。現在地から最も早く着く候補のうち、
「行って・滞在して・帰着地点まで戻る」が活動時間帯に収まるものだけを採り、
収まらなくなったら打ち切って `leftovers` に落とす。ペースは滞在時間と 1 日の件数上限に効く。
`must_place_ids` は距離やペースの件数上限より先に評価し、活動時間帯に収まる限り必ず日割りへ入れる。

### 交通機関が軸であること

移動時間は 2 系統で出す。

- `routes` … Google Routes API の実所要 (キーあり + `use_routes_api`)
- `estimate` … 直線距離 × 迂回係数 ÷ 手段別の実効速度 + 固定オーバーヘッド (キー不要・決定的)

公共交通は待ち・乗換で実効速度が落ちるため 30km/h + 12 分、車は 40km/h + 駐車 10 分、というように
手段ごとに別のモデルを使う。区間ごとの手段は既存の `suggestSegmentMode` に従い、500m 以内は徒歩になる。

どちらで出したかは `duration_source` で必ず示す。概算を実所要のように見せない。

選抜は概算 (無料・同期) で行い、採用した区間だけ実所要で確定させる。
全候補を実 API に問い合わせると呼び出しが日数 × 候補数に膨らむため。
実所要で収まらなくなった候補はその日から外して他を探す。

### LLM の役割

移動と滞在の計算は決定的に済ませてあり、LLM は各日の見出しと一言メモを付けるだけ。
順番や所要は動かさない。失敗しても日割りは成立し、「N 日目」のまま返す。

## データ

新しいテーブルは無い。既存の `trip_check_items` / `trip_days` / `itinerary_items` /
`place_facilities` / `trip_place_facility_wants` をそのまま使う。
